\chapterAndLabel{Purity Checker}{purity-checker}

A \emph{side-effect-free} method is one that changes no object that exists
when it is called.
A \emph{deterministic} method returns the same value each time it is called
on the same arguments.
A \emph{pure} method is both side-effect-free and deterministic.
The Purity Checker can check and infer all three types of methods,
and ``purity'' refers to all concepts.

All checkers utilize purity annotations to aid type refinement
(Section~\ref{type-refinement}).  By default, purity annotations are
trusted, not checked.

To check purity annotations, pass \<-AcheckPurityAnnotations> to any
checker.
To run \emph{only} the Purity Checker (this is uncommon),
supply the following command-line option to javac:
\code{-processor org.checkerframework.framework.util.PurityChecker}.

To infer purity annotations,
supply the command-line option \<-AsuggestPureMethods>.
The Checker Framework will suggest methods that can be marked as
\<@SideEffectFree>, \<@Deterministic>, or \<@Pure>.
In addition, such suggestions are output by \<-Ainfer> and when using
whole-program inference.


\sectionAndLabel{Purity annotations}{purity-annotations}

\begin{description}

\item[\refqualclass{dataflow/qual}{SideEffectFree}]
  indicates that the method has no externally-visible side effects.

\iffalse
\item[\refqualclass{dataflow/qual}{SideEffectsOnly}]
  indicates that the method has limited externally-visible side effects.
\fi

\item[\refqualclass{dataflow/qual}{Deterministic}]
  indicates that if the method is called multiple times with identical
  arguments, then it returns the identical result according to \<==>
  (not just according to \<equals()>).

\item[\refqualclass{dataflow/qual}{Pure}]
  indicates that the method is both \<@SideEffectFree> and \<@Deterministic>.

\end{description}


\sectionAndLabel{Lambdas, method references, and functional interfaces}{purity-functional-interfaces}

Creating a lambda, or declaring a local or anonymous class, is not itself a
side effect.  A lambda expression evaluates to an object but does not run the code
in the lambda's body.  A side-effect-free method may therefore create a lambda
whose body has side effects:

\begin{Verbatim}
  @SideEffectFree
  Runnable makeRunnable() {
    return () -> count++;  // OK: creating the lambda has no side effect
  }
\end{Verbatim}

\noindent
The effects of the body occur where the functional method is invoked, and
each such invocation is checked on its own.

The body of a lambda is checked against the purity annotations on the
functional interface method that the lambda implements, not against those on
the method that creates the lambda.  For example:

\begin{Verbatim}
  @FunctionalInterface
  interface PureSupplier {
    @SideEffectFree String get();
  }

  PureSupplier s1 = () -> "hello";                  // OK
  PureSupplier s2 = () -> { count++; return ""; };  // error: the body has a side effect
\end{Verbatim}


\subsectionAndLabel{Functional-interface parameters of side-effect-free methods}{purity-functional-interface-parameters}

For a side-effect-free method, the functional method of any parameter that is
a functional interface is treated as side-effect-free.

\begin{Verbatim}
  @SideEffectFree
  int m(Function<String, Integer> f, String s) {
    return f.apply(s);  // permitted: apply is treated as side-effect-free
  }
\end{Verbatim}

At calls to \<m>, the functional method of the argument's declared type must
be \<@SideEffectFree>.

\begin{Verbatim}
  m(String::length, "hi");  // OK: String.length() is side-effect-free
\end{Verbatim}

If the argument is a lambda, then the body of the lambda is checked directly
for side effects.

\begin{Verbatim}
  m(s -> s.length(), "hi");  // OK: the lambda body is side-effect-free
  m(s -> count++, "hi");     // error: the lambda body has a side effect
\end{Verbatim}

\sectionAndLabel{Purity annotations are trusted}{purity-trusted}

By default, purity annotations are trusted by every checker built with the
Checker Framework, and the Purity Checker is not run.  However, you can make a
mistake
%
by writing \refqualclass{dataflow/qual}{SideEffectFree} on the
declaration of a method that is not side-effect-free,
%
\iffalse
by writing \refqualclass{dataflow/qual}{SideEffectsOnly} on the
declaration of a method that side-effects more than the listed expressions,
\fi
or
%
by writing \refqualclass{dataflow/qual}{Deterministic} on the
declaration of a method that is not deterministic.

To run the Purity Checker together with another checker, supply the
command-line option \<-AcheckPurityAnnotations>.  The Purity Checker is not
enabled by default because of a high false
positive rate.  In the future, after a new purity-checking analysis is
implemented, the Checker Framework will default to checking purity
annotations.


\sectionAndLabel{Overriding methods inherit specifications from overridden methods}{purity-override}

A purity annotation is inherited:  if a method in a superclass or
superinterface has a purity annotation, then every overriding definition has
that annotation too, even if the annotation is not written on the overriding
definition.  An overriding definition may strengthen the specification by
writing a stronger annotation, but it cannot weaken it.

For example, the \<Object> class is annotated as:

\begin{Verbatim}
class Object {
  ...
  @Pure int hashCode() { ... }
}
\end{Verbatim}

\noindent
(where \refqualclass{dataflow/qual}{Pure} means both
\refqualclass{dataflow/qual}{SideEffectFree} and
\refqualclass{dataflow/qual}{Deterministic}).  Therefore, every definition
of \<hashCode>, including those in your program, is implicitly annotated
as \<@Pure> and its body is checked accordingly:

\begin{mysmall}
\begin{Verbatim}
MyClass.java:1465: error: [purity.not.deterministic.not.sideeffectfree.assign.field] field assignment not allowed in deterministic side-effect-free method
    this.hash = h;
        ^
\end{Verbatim}
\end{mysmall}

\noindent
You can fix the definition by making its body pure.  Alternately, you can
suppress the warning; see \chapterpageref{suppressing-warnings}.


\sectionAndLabel{Suppressing warnings}{purity-suppress-warnings}

The command-line options \<-AassumeSideEffectFree>,
\<-AassumeDeterministic>, and \<-AassumePure> make the Checker Framework
unsoundly assume that \emph{every} called method is side-effect-free, is
deterministic, or is both, respectively.

The command-line option \<-AassumePureGetters> makes the Checker Framework
unsoundly assume that every getter method is side-effect-free and
deterministic.  For the purposes of \<-AassumePureGetters>, a getter method
is defined as an instance method with no formal parameters, whose name
starts with ``get'', ``is'', ``not'', or ``has'' followed by an uppercase
letter.

These options can make
flow-sensitive type refinement much more effective, since method calls will
not cause the analysis to discard information that it has learned.
However, these options can mask real errors.  They are most appropriate when one
of the following is true:
\begin{itemize}
\item
  You are starting out annotating a project.
\item
  You are using the Checker Framework to find bugs but not to give a
  guarantee that no more errors exist of the given type.
\item
  You are working with an unannotated library that makes the given
  assumptions, in which case (say) using \<-AassumePureGetters> is easier
  than writing stub files for all the library's getter methods.
\end{itemize}
